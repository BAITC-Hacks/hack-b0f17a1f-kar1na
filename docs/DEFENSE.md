# WindAI: сценарий защиты и доказательства

Это соответствие опубликованным критериям, а не самоприсвоенная оценка. Итоговые баллы выставляет жюри.

## Демонстрация за 5 минут

1. **Задача (30 секунд).** Диспетчер видит почасовой прогноз нормализованной мощности двух турбин на 24–48 часов. Все пользовательские даты — Астана UTC+05.
2. **Рабочий продукт (45 секунд).** Открыть Overview, выбрать турбину, переключить 24/48 часов и переместить ползунок времени. Показать прогноз, эмпирический интервал и предупреждения. Скачать CSV.
3. **Настоящие действия агента (90 секунд).** Открыть AI Agent и запустить запрос «Построй прогноз, проверь данные и сравни качество с базовым прогнозом». Раскрыть вызовы инструментов: проверка истории, погодный источник, ML-расчёт, анализ риска и январские метрики. Показать, что численные значения совпадают с прогнозом интерфейса.
4. **Обновление и устойчивость (45 секунд).** Нажать «Проверить обновления». При неизменных входах сохраняется прежний `run_id`; при новых входах создаётся версия и сравнение. Монитор проверяет обе турбины каждые 30 минут, пока API запущен. Сбой OpenAI не подменяется успешным ответом: возвращается явно обозначенный резервный численный расчёт.
5. **Честная проверка качества (45 секунд).** Открыть Analytics. MAE на январе: 0.2464 / 0.2555; простой baseline 0.3352 / 0.3328. Снижение ошибки 26.49% / 23.24%. Это качество замороженной оценочной модели на январе; за февраль фактов нет.
6. **Воспроизводимость (45 секунд).** Показать `make test`, `make verify`, документацию API и `results/submission_evidence.json`. Февраль: 56 ежедневных расчётов × 48 часов = 2688 строк. Погода — архив прогнозов, а не фактическая погода.

## Как устроено решение

`OpenAI → inspect_inputs → run_forecast → assess_forecast → read_validation / compare_revision → ответ`.

OpenAI выбирает инструменты и объясняет доказанные результаты. Сервер фиксирует турбину, горизонт и origin, проверяет последовательность и ограничивает вызовы. Модель не получает ключ в промпте, не исполняет произвольный код, не меняет модель мощности и не может отключить проверки будущих данных. При вопросе о качестве сервер требует чтение отчёта валидации до успешного завершения.

Численный агент получает архив/текущий прогноз, проверяет данные, строит признаки, вызывает HistGradientBoosting, проверяет результат и сохраняет его атомарно. При изменении входов вычисляются отличия на пересечении целевых часов. Все промежуточные решения доступны в журнале tools.

## Вопросы жюри и точные ответы

**Почему не показано качество февраля?** В обеих выданных таблицах последняя запись — 31 января 23:50. Поэтому фактические февральские значения и метрики отсутствуют. Прогнозы за весь месяц сформированы и готовы к внешней проверке.

**Есть ли утечка будущего?** История строго раньше origin; training/calibration cutoff не позже origin. Архивные GFS значения берутся на фиксированном lead 72 часа. Для 48-часового горизонта даже после 12-часового допуска на публикацию расчётная граница доступности раньше origin. Это консервативная оценка по семантике API, а не точное время публикации конкретного выпуска. Сохраняются URL запросов и хеш ответа.

**Почему нет МВт·ч и общей выработки станции?** Выданы нормализованные мощности без номинальных мощностей турбин. Складывать их как МВт нельзя. Интерфейс сохраняет единицы 0–1; после получения мощностей можно корректно рассчитать энергию и взвешенный итог станции.

**Что значит 90% интервал?** Номинальный уровень, выбранный по декабрьским остаткам. Измеренное покрытие на январе около 88.1% и 87.8%, поэтому гарантия 90% не заявляется. Для deployment refit, устаревших данных и live-погоды нужна отдельная проверка покрытия.

**Что происходит без интернета?** Replay использует сохранённый архив и модель. OpenAI может стать недоступен: численная часть продолжает работу, языковой режим явно помечается как резервный. Для текущей погоды нужен интернет; наблюдения не подменяют прогноз молча.

**Что дальше?** Первое полезное развитие — доступ к свежей SCADA и точным временам публикации погодных выпусков, затем проверка live-точности, несколько источников погоды и интеграция в процесс планирования. Публичный многопользовательский запуск требует аутентификации, rate limits и постоянного хранилища.
